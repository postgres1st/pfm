# Design: transport security for exporter endpoints (P0.4 steps 2 and 3)

**Status:** proposed — no code written
**Precedes:** any implementation; this exists so the mTLS work is scoped rather than assumed
**Follows:** `fix/p0-4-exporter-security`, which gave each agent a real credential

---

## 1. What is actually true today

Every claim here was checked against the tree, because the last document written on
this subject rested on three assertions that turned out to be wrong.

**The exporter endpoints carry no TLS at all.** The entire web configuration the server
generates is three lines (`managed/models/agent_model.go:1025`):

```yaml
basic_auth_users:
    pmm: {{ . }}
```

There is no `tls_server_config`, no `client_auth_type`, no `client_ca_file` anywhere in
the tree. `scrapeConfigForStandardExporter` sets no `Scheme`, so Prometheus defaults to
`http`, and the two places that do set one pair it with `InsecureSkipVerify: true`
(`scrape_configs.go:125`, `:635`).

**So the credential P0.4 introduced crosses the network in cleartext on every scrape.**
That work replaced a *guessable* credential — the agent ID, which the inventory API
returns — with an unguessable one. It did not make the channel confidential. Against an
observer on the same network the two are worth the same.

The loopback default shipped alongside it mitigates this for the common case: a
push-mode service has no listener reachable off-host, so there is nothing to observe.
It does nothing for `--metrics-mode=pull`, which is exactly the configuration where the
credential travels furthest.

## 2. What exists to build on

**A distribution channel, already in use.** `SetStateRequest_AgentProcess.TextFiles`
carries file *contents* from server to agent; the agent materialises them into its temp
directory and substitutes the paths into the process's arguments through the template
delimiters. This is how `webConfig` already reaches the exporter today
(`agents.ensureAuthParams`), and how Nomad's CA, certificate and key reach the Nomad
agent (`agents/nomad.go:141-146`). **Nothing new is needed to ship certificates.**

**A feature-gating mechanism.** `version.Parsed.IsFeatureSupported` plus per-feature
version constants (`version/features.go`) already gate exporter behaviour on agent
version — `ensureAuthParams` uses it to choose between a web config and the legacy
`HTTP_AUTH` environment variable. A mixed fleet during upgrade is a solved problem
here, not a new one.

**What does NOT exist: a reusable issuer.** The Nomad PKI is generated by shelling out
to the `nomad` binary — `nomad tls ca create`, `nomad tls cert create`
(`services/nomad/nomad.go:149`, `:173`). It cannot be reused:

- it depends on the Nomad binary being installed, and Nomad is optional
  (`PMM_ENABLE_NOMAD`, off in the shipped units)
- it issues **one global client certificate** (`global-client-nomad.pem`), not one per
  agent, so it authenticates "some agent" rather than "this agent"
- the CA is created with `-days 10000` — roughly 27 years, with no rotation path

That last point is a precedent to avoid rather than follow. An exporter PKI needs its
own issuance, in Go, using `crypto/x509`.

## 3. Step 2 — server-side TLS on the exporter endpoint

The smaller and much cheaper half, and it removes the cleartext credential on its own.

**Server side.** Extend `webConfigTemplate` with `tls_server_config`, and ship the
certificate and key alongside `webConfig` in `TextFiles`. The exporter-toolkit reads
both from the same file, so no exporter change is needed.

**Scraper side.** Set `Scheme: "https"` for standard exporters and give the scrape
config a `tls_config` naming the CA. **Drop `InsecureSkipVerify`** — leaving it set
would make the whole exercise theatre, since an attacker who can intercept can present
any certificate.

**Certificate identity.** The scrape target is `node.Address:port` in pull mode and
`127.0.0.1:port` in push mode, so the certificate needs a SAN covering whichever the
scraper will use. This is the first real design question (§6).

**Cost:** one certificate per agent, one CA, no client-side PKI. The agent already
receives files it did not have to request.

## 4. Step 3 — mTLS

**Server side.** Add `client_auth_type: RequireAndVerifyClientCert` and
`client_ca_file` to the same `tls_server_config`, and ship the CA to the agent.

**Scraper side.** Add the client certificate and key to the scrape config's
`tls_config`. VictoriaMetrics reads them from disk, so they need a path on the server,
not a `TextFiles` entry.

**What this buys over step 2:** mutual authentication, and the shared secret disappears
from the scrape configuration entirely. Basic auth can then be dropped for agents new
enough to support mTLS, so there is no longer a bearer credential to leak.

**What it costs — and this decides whether it is an improvement at all:**

| Concern | Consequence if skipped |
|---|---|
| Issuance at registration | agents cannot be added without a manual step |
| Renewal before expiry | the fleet goes dark on a date nobody is watching |
| Revocation on removal | a decommissioned agent keeps a valid identity indefinitely |
| CA rotation | one compromise is unrecoverable without reinstalling every agent |
| Clock skew tolerance | agents with drifting clocks fail to authenticate intermittently |

A PKI without renewal and revocation is *worse* than a well-managed shared secret,
because it carries the same risk plus an expiry cliff. If the lifecycle is not being
committed to, step 2 alone is the better place to stop, and that is a legitimate
outcome of this document rather than a failure of it.

## 5. Sequencing, and why not both at once

1. **Step 2 first.** It removes the cleartext exposure — the actual defect — and
   establishes the certificate plumbing, SAN choice and version gating that step 3
   needs. It is independently shippable and independently valuable.
2. **Step 3 after**, reusing that plumbing, with the password path retained for agents
   older than the mTLS feature version.

Building both together means designing the certificate lifecycle before anything has
exercised the distribution path, which is how the interface ends up wrong.

**Basic auth is not removed by either step.** `ensureAuthParams` already falls back to
`HTTP_AUTH=pmm:<password>` for agents below `v2_28_00`, and a mixed fleet is normal
during an upgrade. The credential stays; it stops being the *only* protection.

## 6. Decisions this document cannot make

1. **Certificate identity.** Per-agent certificates give real per-agent authentication
   and make revocation meaningful, but require issuance at registration. One shared
   certificate is far simpler and is what Nomad does today — and authenticates nothing
   in particular. Recommendation: per-agent, or step 2 only.
2. **Lifetime and renewal.** Short-lived certificates with automatic renewal over the
   existing agent channel, or long-lived ones with a documented manual rotation. The
   `-days 10000` precedent should not be repeated either way.
3. **Whether to do step 3 at all.** If the answer to (2) is "we will not build
   renewal", the honest answer is to stop after step 2.
4. **SAN contents**, following from the pull/push address question in §3.

## 7. Verified vs assumed

**Verified in the tree:** the web config template's contents; the absence of any TLS
server config; `InsecureSkipVerify` at both sites; that standard exporters set no
scheme; the `TextFiles` mechanism and its use for both `webConfig` and Nomad's certs;
that the Nomad PKI shells out to the `nomad` binary, issues a single global client
certificate and uses `-days 10000`; that Nomad is optional; and the existence of
version-based feature gating.

**Assumed, and to confirm before implementing:** that the exporters support
`tls_server_config` and `client_auth_type`. This one cannot be settled from this
repository at all — `exporter-toolkit` is not a dependency here; the exporters are
separate binaries shipped by `pfw-client`, so their toolkit version has to be read
from the built package or the exporter forks. The upstream documentation the template
already links to describes both fields, but that is the toolkit's current version, not
necessarily the one shipped. **Check this first: if the shipped exporters are too old,
step 2 is blocked before any design question matters.** The pins to check are in
`build/scripts/pfw-airgap-vars` — `PFW_NODE_EXPORTER_REPO` /
`PFW_POSTGRES_EXPORTER_REPO` and their accompanying commit or tag variables — which
name the `percona/*_exporter` forks this bundle actually builds. Also unconfirmed: that
VictoriaMetrics' scrape config accepts the client certificate fields in the form the
generator would produce.

**Not investigated:** whether any UI surface displays or depends on the exporter scheme;
and the RDS and Azure exporters, which bind all interfaces with no authentication at all
and are out of scope for both steps — they need their own decision, recorded in
`managed/services/agents/rds.go`.
